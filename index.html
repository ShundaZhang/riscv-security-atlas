02 / TRANSFER YOUR INTUITION

用旧知识定位，用新规则推理。

这些是功能上的类比，不是一一对应的架构等价关系。先找出熟悉的概念，再关注会影响内核、虚拟化和安全实现的差异。

你已熟悉RISC-V 对应入口需要重建的直觉
x86 指令 / A64RV64I + 扩展；-march / -mabiISA 是模块化的。RV64 不等于某套完整平台能力；二进制 ABI 也不由寄存器宽度独自决定。
RFLAGS / NZCVbeq / blt / bltu、slt基础整数 ISA 没有通用条件码寄存器；分支直接比较寄存器。区分有符号和无符号比较。
call / ret、LRra=x1、jal / jalr返回地址写寄存器，非叶函数通常需保存 ra。标准 RV64 ABI 的 sp 对齐 16 字节；栈下方没有可依赖的 red zone。
Ring 3/0、EL0/1/2/3U / S / M；H 扩展下 HS / VS / VUM 是机器特权级；安全域是另一维度。M 不等于 EL3 或 Secure world。HS 是启用 H 后的宿主 supervisor 环境。
syscall / SVC / HVC / SMCecall 与不同 ABI同一个指令可用于用户系统调用、SBI 或 guest SBI。调用者模式、trap delegation 和软件 ABI 决定去向及语义。
CR3 / TTBR、TLBIsatp、Sv39、sfence.vma写 satp 本身不是完整的翻译同步。地址空间切换和权限撤销要考虑本地 fence、ASID 与其他 hart。
EPT/NPT / stage-2vsatp + hgatpVS-stage：GVA → GPA；G-stage：GPA → SPA。宿主若控制二阶段页表，普通 VM 本身无法对它保密。
x86 TSO / Arm 弱内存序默认 RVWMO；原子操作与 fence不要搬运“在 x86 恰好可用”的发布逻辑。C/C++ 用标准原子；fence、fence.i、sfence.vma解决不同问题。
MPU / 物理访问控制PMP / SmepmpPMP 关注 hart 的物理访问授权，不做虚拟地址翻译；设备 DMA 要另查 IOMMU 与平台互连的保护。
SGX / TrustZone / SNP / TDX / CCAEnclave、平台 TEE、CoVE TVM先比较保护对象、TCB 和攻击者能力。CoVE 的主线是机密虚拟机，不能把所有 TEE 都理解成同一种 enclave。

核对入口：RV64I · psABI · H 扩展 · RVWMO。平台类比是本手册的教学归纳。

30 分钟快速定位

10 分钟读这张对照表，10 分钟看下方执行栈，10 分钟读 CoVE 的威胁模型。先能回答“谁能读哪一页、谁能修改授权”，再深入 CSR 位定义。

常见非虚拟化 Linux 执行栈

U-mode    应用
  │ ecall / syscall ABI
S-mode    Linux
  │ ecall / SBI（部分平台服务）
M-mode    OpenSBI / 平台固件
  │
硬件       PMP · 中断控制器 · 内存 / I/O

这是常见部署示意。启动链因平台而异，OpenSBI 也不意味着所有 timer 操作都必须陷入 M-mode。

加入 H 扩展之后

VU        Guest 应用
VS        Guest 内核 ─ vsatp ─ GVA → GPA
  │ trap / SBI emulation
HS        Host Linux + KVM
          hgatp ─ G-stage ─ GPA → SPA
M         平台固件

hart 指硬件线程；CSR 是控制状态寄存器。这里描述执行权限，不是 TEE 信任图。

03 / THE LEARNING PATH

每一阶段，都带着一个安全问题。

按需展开

预计总计 40–60 小时量级，按下面各阶段估算约 40–60+ 小时；取决于已有内核经验。规范精读与 CoVE 环境复现可额外花数天。每阶段按“导读 → 实验 → 查规范 → 验收”推进。

01

读懂代码：ISA、ABI 与内存序

4–6 小时 · 前置：C、汇编、ELF 基础

本阶段要解决什么

拿到一段 RISC-V 反汇编，能恢复参数、调用链和数据宽度；审查跨 hart 的共享状态时，知道哪些 x86 假设不能保留。

  • 抓住 load/store、比较分支、auipc、jalr。li / call / ret 是汇编伪指令；启用 C 扩展时指令可能只有 16 位，不能总按 PC+4 走。
  • 重点看 lw 与 lwu、addw 的扩展行为。32 位结果与 64 位寄存器之间的转换，是移植和参数验证的高频陷阱。
  • 看懂 a0–a7、ra、sp、s0–s11；区分 ISA 选择与 ABI 选择，理解链接松弛会使最终指令序列不同于编译阶段。
  • 认识 LR/SC、AMO 与 acquire/release；先用语言级原子表达同步，再检查编译器生成。不要把 volatile 当作同步原语。

只读这些

RV64I：整数运算、访存；psABI：Register / Procedure Calling Convention、Linker Relaxation；RVWMO：模型概览。暂缓向量、浮点细节和完整编码表。

实践与交付

做 实验 1，保存一份有注释的反汇编；分别说明参数、返回值、栈、32 位运算和最终 ELF 属性。

验收：为什么 RV64 的 lw 后，高 32 位不一定为零？

lw 将 32 位值符号扩展到 XLEN；lwu 才是零扩展。再解释为什么函数返回值还要结合类型和 ABI，而不能仅凭某条 load 推断。

02

掌握控制流：特权、Trap 与 Sv39

8–10 小时 · 前置：阶段 01

本阶段要解决什么

应用越权访问后，硬件在哪一层拒绝，控制流交给谁，返回时恢复了什么？

  • 将 trap 分成同步异常和异步中断。追踪 stvec / sepc / scause / stval / sstatus；用 medeleg / mideleg 理解委托，不能假定所有 ecall 都先到 M。
  • 硬件不会替软件保存完整通用寄存器集、切好内核栈并换好页表。用 xv6 的 trampoline 将这些步骤逐一对上。
  • Sv39 的典型 4 KiB 页：虚拟地址拆成 9/9/9/12 位；三层 PTE。检查 V/R/W/X/U/A/D 与叶子项、superpage；无效编码和权限错误也参与失败判定。
  • 区分 page fault 与 access fault；前者多与地址转换 / 页表权限有关，后者可来自物理访问授权或平台访问失败。SUM/MXR 的权限影响也要单独查。

只读这些

Supervisor：trap CSR、satp、Sv39、SFENCE.VMA；MIT 6.1810：Page tables、System call entry/exit、Traps lab。xv6 只抓 trampoline.S → trap.c → syscall.c 和 vm.c。

实践与交付

做 实验 2，画一条 U → S → U 路径，注明每一步谁负责；再追踪一个 guard-page fault，记录原因与故障地址。

验收：改了 PTE，为什么不能立即假定所有 CPU 都失去访问权限？

内存中的 PTE 不是所有 hart 已生效的翻译状态。需按地址空间与并发协议执行本地翻译同步，并协调远程 hart 的 shootdown。隔离撤销必须以旧访问能力确实失效为完成条件。

03

找到可信底座：PMP、SBI 与启动

6–8 小时 · 前置：阶段 02

本阶段要解决什么

如果 Linux 被攻陷，固件如何保住自己的代码和数据？“能启动”与“可信启动”之间还缺什么？

  • PMP 用物理地址范围与 R/W/X 做访问检查。先理解 TOR / NAPOT、匹配优先级、锁定位和无匹配时的规则，再看 Smepmp 对 M-mode 约束的增强。
  • 不要把标准 PMP 的 M-mode 默认行为笼统说成“永远绕过”或“全部受限”；锁定、有效特权、MPRV 与 Smepmp 都会改变判断。
  • SBI 是接口规范，OpenSBI 是实现。先理解 Base extension 的能力探测，再看 TIME、IPI、RFENCE、HSM；不要根据 CPU 名称猜测可用扩展。
  • 把启动链拆成加载、签名验证、度量和运行期隔离。固件保留内存应与 Linux 使用的内存描述一致；DT 的 no-map 约定不等于硬件访问控制。

只读这些

Machine：Physical Memory Protection；Smepmp；SBI；OpenSBI；Linux boot requirements。

实践与交付

做 实验 3。记录固件版本、next-stage mode、内存范围；在纸上列出 M/S/U 对每个 PMP 区域的读写执行权限，不要用一句“高特权可信”代替证明。

验收：CPU 的 PMP 配好了，设备 DMA 就不能读秘密了吗？

不能据此得出结论。PMP 是 hart 侧机制；必须确认 DMA 路径上的 IOMMU、互连防火墙、设备授权以及固件配置是否形成完整的访问控制。

04

进入虚拟化：H 扩展、KVM 与 I/O

8–12 小时 · 前置：阶段 02–03；已有 KVM 经验可加速

本阶段要解决什么

普通 VM 的隔离信任宿主。要进一步保护 VM 不受恶意宿主影响，必须先看清宿主原本掌握的能力。

  • 将 VS/VU 和 HS 放到正确位置；理解 hstatus、虚拟化 CSR 以及 guest trap 如何进入宿主。
  • 画 GVA → GPA → SPA 两阶段路径；不要把 vsatp 与 hgatp 的地址空间混在一起。按规范区分 HFENCE.VVMA 与 HFENCE.GVMA 的同步对象。
  • 在 Linux arch/riscv/kvm/ 里追踪 vCPU 进入 / 退出、SBI 模拟与二阶段缺页。阅读实际 checkout，文件拆分会随版本变化。
  • AIA / IMSIC 帮助理解中断虚拟化；IOMMU 处理设备访问路径。二者都不能只凭“启用”就推导完整机密计算保证。

只读这些

H 扩展：CSR、two-stage translation、traps；Linux RISC-V KVM 源码；AIA；IOMMU。只先读 overview 和编程模型。

实践与交付

完成 实验 4 的翻译与源码追踪。有支持 H 的 RISC-V 环境再做 KVM 启动；在 x86/Arm 上用 QEMU TCG 跑 RISC-V，不等于跨架构 KVM 加速。

验收：Guest 页表禁止宿主访问，是否就能实现机密 VM？

Guest 页表约束 guest 自身的转换。普通宿主仍管理 guest 物理内存及二阶段映射；CoVE 需要由可信组件和平台隔离机制约束不可信宿主对 TVM 的访问。

05

把安全目标写清楚：TEE 与 Attestation

6–8 小时 · 前置：阶段 03–04

本阶段要解决什么

“可信”是相对于资产、攻击者和假设而言。远程工作负载拥有者凭什么向这台机器交付秘密？

  • 资产包括私有内存、寄存器状态、密钥与初始度量；攻击面包括宿主、设备、共享缓冲区、异常输入和调试接口。
  • 把 TCB（Trusted Computing Base）列为具体组件。硬件根、M-mode 固件、TSM 和 guest 内部可信代码，不会因为宿主移出 TCB 就消失。
  • 区分 secure boot（验证是否允许启动）、measured boot（记录启动了什么）、attestation（输出可验证证据）和 verifier policy（判定是否接受）。
  • 共享页既可能被读，也可能被篡改。练习长度 / 偏移校验、复制后校验、双取数风险和明确的缓冲区所有权，不要在未校验输入上使用特权。

只读这些

CoVE threat model → Attestation and Measurements；再用 Keystone 对照 enclave 模型。Keystone 是另一条 TEE 设计路线，不是 CoVE 的同义词或必经依赖。

实践与交付

做 实验 5 的威胁模型评审：一页资产 / 攻击者 / 假设表，一张 TCB 图，一份“拒绝释放密钥”的反例集合。

验收：证明报告签名有效，就应该把密钥发给 guest 吗？

还要检查信任链、度量是否在允许列表、TCB 版本与策略、新鲜度，以及接收密钥的会话 / 公钥是否绑定到已验证的环境。签名有效只说明证据通过了部分验证。

06

走向 CoVE：生命周期、内存归属与证明

8–16 小时导读 · 环境复现另计 · 前置：阶段 01–05

本阶段要解决什么

把规范角色与实际调用链连起来：宿主请求创建 TVM，TSM 校验并执行受保护操作，guest 与外界通过显式接口协作。

  • TVM（TEE VM）是受保护虚拟机；TSM（TEE Security Manager）是可信安全管理组件。TSM 的执行模式依部署模型变化，不要固定理解为“必须跑在 HS”。
  • 从 COVH（host）、COVG（guest）、COVI（interrupt）接口分工入手，再查当前草案的调用前置条件与错误。ABI 不是一条万能的 CPU 安全指令。
  • 沿 TVM 的创建、页面装入与度量、finalize、执行、销毁，逐步问“这时允许谁访问”。Private/shared 转换要与映射撤销、并发、缓存 / TLB 和清零协议一同分析。
  • 将 Smmtt / Supervisor Domains 的硬件隔离工作与 CoVE 的软件接口分层阅读；CoVE-IO 再扩展到设备信任与安全直通。

最短阅读顺序

Threat model → Reference architecture → SBI interfaces → Attestation → 选一份实现追调用链。

实践与交付

按 实验 6 固定版本组合，输出一份可复现记录。最终用下方 CoVE 阅读地图 做一次设计评审；不把研究实现默认当生产方案。

验收：TSM 的代码很小，TVM 的 TCB 就很小吗？

不一定。还需纳入实际依赖的平台硬件、固件、证明根、设备及 guest 内部组件。TCB 取决于保护对象与部署模型，不等于一个仓库的代码量。

选修顺序

先补 AIA / IOMMU 与 RVWMO；之后按岗位补 Zicfiss / Zicfilp 控制流保护、密码扩展、微架构侧信道。V 扩展和 RTL 不在通往 CoVE 的最短主线上。

04 / LEARN BY OBSERVING

从一份反汇编，到一份安全评审。

实验 1–3 给出起步命令，4–6 是源码与安全分析任务。命令环境按 Ubuntu 24.04 / Debian 系 Linux 编写；macOS 建议在 Linux VM 中执行。以下是学习配方，本手册未在目标 Linux 环境逐项实跑，不将预期输出冒充测试结果。

L1 · USER SPACE

观察一段 C 的 ABI 与机器码

安装交叉工具链和模拟器，编译 Linux 用户态程序。此处选 rv64gc/lp64d 匹配常见发行版工具链；不要求你先学完浮点。

sudo apt update
sudo apt install build-essential git gcc-riscv64-linux-gnu \
  binutils-riscv64-linux-gnu libc6-dev-riscv64-cross \
  qemu-user qemu-system-misc gdb-multiarch

mkdir -p riscv-lab1
cd riscv-lab1
cat > abi.c <<'C'
#include <stdint.h>
#include <stdio.h>
__attribute__((noinline))
int32_t add32(int32_t a, int32_t b) { return a + b; }
int main(void) { printf("%d\n", add32(40, 2)); return 0; }
C
riscv64-linux-gnu-gcc -O0 -g -march=rv64gc -mabi=lp64d -S abi.c -o abi-O0.s
riscv64-linux-gnu-gcc -O2 -g -march=rv64gc -mabi=lp64d -static abi.c -o abi
riscv64-linux-gnu-objdump -d -M no-aliases abi > abi.dis
riscv64-linux-gnu-readelf -h -A abi
qemu-riscv64 ./abi

预期：输出 42；在 add32 附近寻找 32 位加法及返回序列。比较 O0 的栈帧与 O2 的叶函数，不要求每个编译器都生成相同文本。

排错：静态链接找不到 libc 时，检查交叉 libc 开发包；动态程序找不到 loader 时，用匹配的 sysroot 配合 QEMU -L。不要把用户态 QEMU 当整机模拟器。

验收产物：给 a0/a1、a0 返回值、ra、指令长度和 ELF ABI 标注；将 add32 改为无符号类型，解释语义而不依赖输出外观。

L2 · TRAP & PAGE TABLE

在 xv6 中停住一次系统调用

先按 MIT 当前工具要求安装足够新的 QEMU；如果发行版自带版本太旧，应升级后再继续。保留克隆的具体提交，避免课程实验分支与主仓库混用。

git clone https://github.com/mit-pdos/xv6-riscv.git
cd xv6-riscv
git rev-parse HEAD
qemu-system-riscv64 --version
make TOOLPREFIX=riscv64-linux-gnu- qemu-gdb

在第二个终端进入同一目录。make qemu-gdb 会打印 GDB 端口；以实际端口替换下面的 PORT（不是固定 1234）。

gdb-multiarch kernel/kernel
(gdb) target remote localhost:PORT
(gdb) break usertrap
(gdb) continue
(gdb) p/x $scause
(gdb) p/x $sepc
(gdb) p/x $stval
(gdb) x/8i $pc

观察：初次断住也可能遇到其他 trap，应以 scause 为准。用户态 ecall 的异常码为 8；它与软件选择的 syscall number 是两回事。

交付：读 kernel/trampoline.S 和 kernel/trap.c，标出保存寄存器、换页表、更新 sepc 和 sret 的位置。再完成 MIT 的 page-table / trap lab，对一次故障解释“哪一级拒绝”。

排错：内联或汇编阶段的 C 断点未命中时，用符号地址断点和反汇编；Ctrl-a x 退出 QEMU。xv6 的启动和定时器实现会变化，按你固定的提交阅读。

L3 · FIRMWARE

只启动 OpenSBI，观察 M → S 的交接

这个最小实验使用 OpenSBI 自带测试 payload，刻意把固件观察与完整 Linux 镜像构建拆开。

git clone https://github.com/riscv-software-src/opensbi.git
cd opensbi
git rev-parse HEAD
make CROSS_COMPILE=riscv64-linux-gnu- PLATFORM=generic
qemu-system-riscv64 -M virt -m 256M -smp 1 -nographic \
  -bios build/platform/generic/firmware/fw_payload.bin

观察：OpenSBI banner、平台信息、next-stage 地址与模式；自带 payload 的具体行为以版本为准。编译失败先核对 OpenSBI README 的工具链最低要求。

然后做：阅读 QEMU virt 启动说明，用与你的 kernel/rootfs 匹配的参数启动 Linux；核对 a0 / a1、satp 与固件保留内存约束。记录“固件加载内核”和“验证内核签名”是否真的都发生。

L4 · TRANSLATION

追踪一条 guest 地址

构造一个纸上例子：GVA 0x4000 经 VS-stage 映射到 GPA 0x8000，再映射到 SPA 0x90008000。分别撤销两个阶段的权限，推演陷入哪里。

在你固定的 Linux checkout 中，从 arch/riscv/kvm/ 找到 guest-page-fault 与 SBI 分派路径；写清宿主能否修改映射和访问 backing page。

验收：提交两张转换图、一条调用链；解释普通 KVM 与机密 VM 的新增安全需求。

L5 · THREAT MODEL

设计一个“拒绝放钥”的流程

假设宿主已被攻陷，TVM 要向远程服务申请解密密钥。画出 challenge、evidence、验证策略、会话绑定和密钥交付。

逐项注入反例：重放旧证明、替换接收公钥、改变启动页、共享缓冲区双取数、宿主永不调度。

验收：前三类必须拒绝；共享输入需校验；最后一项应识别为可用性问题，不能伪称 TEE 自动消除。

L6 · CoVE RESEARCH

固定一个版本组合，复现一条 TVM 生命周期

从 CoVE PoC 的 README 选择它明确支持的依赖组合。这里不给未经验证的“一键安装最新版 CoVE”：ABI、宿主内核、TSM 与 QEMU 的分支必须配套。

  1. 记录规范 commit，以及 QEMU、OpenSBI / TSM、host kernel、guest image、VMM 的仓库 URL 与 commit；再记录全部构建参数。
  2. 先跑文档自带 workload，收集 create → populate / measure → finalize → run → destroy 的日志。它是教学上的生命周期概括，实际函数名以固定草案为准。
  3. 确认哪些隔离由模拟模型提供，哪些能力只是 stub / 测试密钥；将 attestation、设备直通、迁移等未实现能力单列。
  4. 设计负向用例：重用已归属页面、非法生命周期调用、宿主访问私有页、错误证明策略。只把实际观察到的结果写成“通过”。

毕业交付：版本清单、TCB 图、页状态转换图、至少三条负向测试记录，以及“这份 PoC 尚不能证明什么”。若环境暂时无法复现，可先完成源码评审，并明确标为静态分析。

05 / THE DESTINATION

CoVE：从 VM 隔离，走向宿主不可信。

规范草案

CoVE（Confidential VM Extension）关注的核心场景是：宿主 OS / VMM 参与创建和调度 TVM，但不应因此获得 TVM 的机密内存与敏感运行状态。具体保证依赖平台实现、硬件隔离、证明根及声明的威胁模型。下图是学习用职责图，不代表唯一的执行模式或完整信任链。

01 / OWNER工作负载拥有者

定义镜像、允许的度量与密钥释放策略。

02 / HOST宿主 OS / VMM

请求资源、创建与调度 TVM；按威胁模型可视为潜在攻击者。

03 / TRUSTEDTSM + TSM-driver

执行受保护操作、维护 TVM 状态及授权；所需硬件 / 固件属于 TCB。

04 / GUESTTVM

运行 guest 固件、OS 与工作负载；通过受控共享区与宿主协作。

05 / VERIFIER证明验证者

核对证据、新鲜度、度量与策略，决定是否交付秘密。

五个必须追问的边界

  1. 所有权：一页从宿主分配给 TVM 后，谁还能建立读写或别名映射？
  2. 转换：私有页转共享 / 回收时，谁负责撤映射、同步、清零与防竞态？
  3. 状态：vCPU 寄存器、异常信息、定时器和中断状态存放在哪？
  4. I/O：DMA 与 MMIO 路径的访问授权由谁控制？设备本身是否可信？
  5. 证明：证据覆盖哪些平台 / TSM / TVM 元素？验证者如何绑定会话？

不要凭空补上的保证

可用性：草案的威胁模型明确把宿主造成的拒绝服务排除在保证之外；宿主可以拒绝调度。看原文

物理与侧信道：攻击者范围和缓解措施与平台方案有关，不能从“CoVE”这一名称推出统一覆盖。看威胁表

设备安全：CPU 访存隔离不自动覆盖 DMA；设备直通另读 CoVE-IO 草案。

版本状态 / 2026.09.23 核对

RISC-V 官方 H 扩展 v1.0 在已批准规范库中。AP-TEE / CoVE ABI 仓库 仍明确标注 development、not ratified；Supervisor Domains / Smmtt 仓库 是独立的硬件隔离规范工作。实验代码的存在不说明全部 CoVE 安全属性已落实；阅读时记录仓库 commit，并复核 规范开发看板。

  3. TVM 私有页是否可能被宿主重映射、别名化或 DMA 访问？
  4. 私有↔共享转换的同步、清零与错误回滚由谁完成？

  3. PoC 哪些路径是真实保护，哪些是模拟、stub 或未来工作？
