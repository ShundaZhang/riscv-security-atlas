02 / TRANSFER YOUR INTUITION

Map familiar concepts; reason with new rules

These are functional analogies, not one-to-one architectural equivalence. Find familiar concepts first, then focus on differences that affect the kernel, virtualization, and security implementation.

You are already familiarRISC-V corresponding entryIntuition that needs to be rebuilt
x86 instructions / A64RV64I + extensions;-march / -mabiISA is modular. RV64 does not equal a complete set of platform capabilities; nor is the binary ABI determined solely by register width.
RFLAGS / NZCVbeq / blt / bltu、sltThe basic integer ISA has no general condition code register; branches compare registers directly. Distinguish between signed and unsigned comparisons.
call / ret、LRra=x1、jal / jalrThe return address is written to the register, and non-leaf functions usually need to save ra. The standard RV64 ABI's sp alignment is 16 bytes; there is no red zone to rely on below the stack.
Ring 3/0、EL0/1/2/3U / S / M; HS / VS / VU under H extensionM is the machine privilege level; the security domain is another dimension. M is not equal to EL3 or Secure world. HS is the host supervisor environment after H is enabled.
syscall / SVC / HVC / SMCecall With different ABIThe same instruction can be used for user system calls, SBI or guest SBI. The caller pattern, trap delegation, and software ABI determine the destination and semantics.
CR3 / TTBR、TLBIsatp、Sv39、sfence.vmaWriting satp itself is not a complete translation synchronization. Address space switching and permission revocation take into account local fences, ASIDs, and other harts.
EPT/NPT / stage-2vsatp + hgatpVS-stage: GVA → GPA; G-stage: GPA → SPA. If the host controls the second-stage page table, the ordinary VM itself cannot keep it secret.
x86 TSO / Arm weak memory orderingDefault RVWMO; atomic operations and fenceDon't carry release logic that "just works on x86". C/C++ uses standard atoms;fence、fence.i、sfence.vmaSolve different problems.
MPU/Physical Access ControlPMP / SmepmpPMP focuses on the physical access authorization of hart and does not perform virtual address translation; the device DMA needs to separately check the protection of the IOMMU and platform interconnection.
SGX / TrustZone / SNP / TDX / CCAEnclave, platform TEE, COVE TVMFirst compare the protected objects, TCB and attacker capabilities. The main line of CoVE is a confidential virtual machine, and all TEEs cannot be understood as the same kind of enclave.

Check entry:RV64I · psABI · H extension · RVWMO. The platform analogy is the pedagogical summary of this manual.

30 minutes for quick positioning

10 minutes to read this comparison table, 10 minutes to look at the execution stack below, and 10 minutes to read CoVE's threat model. First, you can answer "who can read which page and who can modify the authorization", and then go into the definition of CSR bit.

A typical non-virtualized Linux stack

U-mode    Application
  │ ecall / syscall ABI
S-mode    Linux
  │ ecall / SBI (some platform services)
M-mode    OpenSBI / platform firmware
  │
Hardware  PMP · interrupt controller · memory / I/O

This is a common deployment diagram. The boot chain varies between platforms, and OpenSBI does not imply that all timer operations must fall into M-mode.

With the H extension

VU        Guest application
VS        Guest kernel ─ vsatp ─ GVA → GPA
  │ trap / SBI emulation

hart refers to the hardware thread; CSR is the control status register. This describes execution permissions, not the TEE trust graph.

03 / THE LEARNING PATH

Every stage starts with a security question

Deployment on demand

Estimated total time of 40–60 hours, estimated at about 40–60+ hours according to the following stages; depends on existing kernel experience. Specification intensive reading and CoVE environment reproduction can take several additional days. Each stage is advanced according to "Introduction → Experiment → Check Specification → Acceptance".

01

Read code: ISA, ABI, and memory ordering

4–6 hours · Pre-requisite: C, assembly, ELF basics

What to solve at this stage

Get a piece of RISC-V disassembly, which can restore parameters, call chains and data width; review cross-hart Know which x86 assumptions cannot be preserved when sharing state.

  • Grab load/store, compare branches,auipc、jalr.li / call / ret is an assembly pseudo-instruction; when the C extension is enabled, the instruction may only have 16 bits and cannot always follow PC+4.
  • Focus on the extended behavior of lw and lwu、addw . Conversion between 32-bit results and 64-bit registers is a high-frequency pitfall for porting and parameter verification.
  • Understand a0–a7, ra, sp, s0–s11; distinguish ISA selection and ABI selection, and understand that link relaxation will make the final instruction sequence different from the compilation stage.
  • Understand LR/SC, AMO and acquire/release; first express synchronization with language-level atoms, and then check the compiler generation. Don't think of volatile as a synchronization primitive.

Read only these

RV64I: Integer arithmetic, memory access;psABI:Register / Procedure Calling Convention、Linker Relaxation;RVWMO: Model overview. Suspended vectors, floating point details, and full encoding tables.

Practice and Delivery

Do Lab 1, save a commented disassembly; specify parameters, return value, stack, 32-bit arithmetic and final ELF attributes respectively.

Acceptance: Why are the upper 32 bits after lw of RV64 not necessarily zero?

lw sign-extends 32-bit values ​​to XLEN; lwu is zero-extended. Then explain why the function return value must be combined with the type and ABI, rather than just relying on a certain load inference.

02

Control flow: privilege, traps, and Sv39

8–10 hours · Pre-requisite: Phase 01

What to solve at this stage

After applying unauthorized access, at which layer does the hardware deny it, to whom does the control flow go, and what is restored on return?

  • Divide traps into synchronous exceptions and asynchronous interrupts. Track stvec / sepc / scause / stval / sstatus; use medeleg / mideleg Understand delegation and cannot assume that all ecalls arrive at M first.
  • The hardware will not save the complete general-purpose register set, cut the kernel stack, and replace the page table for the software. Use xv6's trampoline to match these steps one by one.
  • Typical 4 KiB page for Sv39: virtual address split into 9/9/9/12 bits; three-layer PTE. Check V/R/W/X/U/A/D, leaf items, and superpage; invalid encoding and permission errors also participate in failure determination.
  • Distinguish between page fault and access fault; the former is mostly related to address translation/page table permissions, while the latter can come from physical access authorization or platform access failure. The permission impact of SUM/MXR should also be checked separately.

Read only these

Supervisor:trap CSR、satp、Sv39、SFENCE.VMA;MIT 6.1810:Page tables、System call entry/exit、Traps lab. xv6 only captures trampoline.S → trap.c → syscall.c and vm.c.

Practice and Delivery

Do Experiment 2, draws a U → S → U path, and indicates who is responsible for each step; then track a guard-page fault and record the cause and fault address.

Acceptance: After changing the PTE, why not immediately assume that all CPUs have lost access?

The PTE in memory is not the translation status of all harts that have taken effect. It is necessary to perform local translation synchronization according to the address space and concurrency protocol, and coordinate the shootdown of remote hart. Quarantine revocation must be completed based on the actual invalidation of the old access capability.

03

Find the trust base: PMP, SBI, and boot

6–8 hours · Pre-requisite: Phase 02

What to solve at this stage

If Linux is compromised, how does the firmware protect its code and data? What's missing between "can start" and "trusted start"?

  • PMP uses physical address ranges and R/W/X for access checks. First understand TOR / NAPOT, match priority, lock bit and the rules when there is no match, and then look at Smepmp’s enhancement of M-mode constraints.
  • Don't generalize the default behavior of standard PMP's M-mode as "bypass forever" or "all restricted"; locking, effective privileges, MPRV and Smepmp will all change the judgment.
  • SBI is the interface specification and OpenSBI is the implementation. First understand the capability detection of Base extension, and then look at TIME, IPI, RFENCE, and HSM; do not guess the available extensions based on the CPU name.
  • Split the startup chain into loading, signature verification, measurement and runtime isolation. Firmware reserved memory should be consistent with the memory description used by Linux; DT's no-map convention is not equivalent to hardware access control.

Read only these

Machine:Physical Memory Protection;Smepmp;SBI;OpenSBI;Linux boot requirements.

Practice and Delivery

Do Experiment 3. Record the firmware version, next-stage mode, and memory range; list the M/S/U read, write, and execute permissions for each PMP area on paper. Do not use the sentence "high privileges and trusted" instead of proof.

Acceptance: Once the CPU's PMP is configured, can the device DMA not be able to read secrets?

No conclusion can be drawn based on this. PMP is a hart-side mechanism; you must confirm whether the IOMMU, interconnection firewall, device authorization, and firmware configuration on the DMA path form complete access control.

04

Enter virtualization: H extension, KVM, and I/O

8–12 hours · Pre-requisite: Stages 02–03; existing KVM experience can accelerate

What to solve at this stage

Isolated trust host for common VMs. To further protect VMs from malicious hosts, you must first understand the capabilities of the host.

  • Place VS/VU and HS in the correct location; understand hstatus, virtualization CSR, and how guest traps enter the host.
  • Draw GVA → GPA → SPA two-stage path; do not mix vsatp and hgatp address spaces. Synchronization objects distinguished by specification HFENCE.VVMA and HFENCE.GVMA .
  • Tracking vCPU entry/exit, SBI emulation and two-stage page faults in Linux arch/riscv/kvm/ . Reading the actual checkout, the file split will change from version to version.
  • AIA/IMSIC helps understand interrupt virtualization; IOMMU handles device access paths. Neither can deduce complete confidential computing guarantees from "enablement" alone.

Read only these

H extensions: CSR, two-stage translation, traps;Linux RISC-V KVM source code;AIA;IOMMU. Just read the overview and programming model first.

Practice and Delivery

Complete Translation and source code tracking of Experiment 4. There is a RISC-V environment that supports H before KVM startup; using QEMU TCG to run RISC-V on x86/Arm does not mean cross-architecture KVM acceleration.

Acceptance: If the Guest page table prohibits host access, can a confidential VM be implemented?

Guest page table constrains the translation of the guest itself. Ordinary hosts still manage guest physical memory and two-stage mapping; COVE requires trusted components and platform isolation mechanisms to restrict access to TVM by untrusted hosts.

05

Define the security goal: TEE and attestation

6–8 hours · Pre-requisite: Phase 03–04

What to solve at this stage

"Trusted" is relative to assets, attackers, and assumptions. Who is the remote workload owner to hand over secrets to this machine?

  • Assets include private memory, register status, keys and initial metrics; attack surfaces include hosts, devices, shared buffers, exception inputs and debugging interfaces.
  • List TCB (Trusted Computing Base) as a specific component. The hardware root, M-mode firmware, TSM and guest internal trusted code will not disappear just because the host moves out of the TCB.
  • Distinguish between secure boot (verify whether startup is allowed), measured boot (record what is started), attestation (output verifiable evidence) and verifier policy (determine whether to accept it).
  • The shared page may be read or tampered with. Practice length/offset checking, post-copy checking, double fetch risks, and clear buffer ownership, and don't use privileges on unchecked input.

Read only these

CoVE threat model → Attestation and Measurements; Then use Keystone to compare the enclave model. Keystone is another TEE design route and is not a synonym or necessary dependency of CoVE.

Practice and Delivery

Do Threat model review for Experiment 5: One page of assets/attackers/hypothesis tables, a TCB diagram, and a set of counterexamples for "refuse to release keys".

Acceptance: To prove that the report signature is valid, should the key be sent to the guest?

Also check the trust chain, whether the metric is in the allowed list, TCB version and policy, freshness, and whether the session/public key receiving the key is bound to an authenticated environment. A valid signature only means that the evidence has passed partial verification.

06

Reach CoVE: lifecycle, memory ownership, and attestation

8–16 hours of introduction · Environment reproduction additional · Pre-requisite: Phase 01–05

What to solve at this stage

Connect the specification role with the actual call chain: the host requests to create a TVM, the TSM verifies and performs protected operations, and the guest collaborates with the outside world through explicit interfaces.

  • TVM (TEE VM) is a protected virtual machine; TSM (TEE Security Manager) is a trusted security management component. The execution mode of TSM changes according to the deployment model, and should not be understood as "must run on HS".
  • Start with the division of labor among COVH (host), COVG (guest), and COVI (interrupt) interfaces, and then check the calling preconditions and errors of the current draft. The ABI is not a one-size-fits-all CPU-safe instruction.
  • Ask along the creation, page loading and measurement, finalize, execution, and destruction of TVM, and gradually ask "Who is allowed to access at this time?" Private/shared transitions are analyzed along with map undo, concurrency, cache/TLB, and zeroing protocols.
  • Read in layers the hardware isolation work of Smmtt/Supervisor Domains and the software interface of CoVE; CoVE-IO is then extended to device trust and security pass-through.

Shortest reading order

Threat model → Reference architecture → SBI interfaces → Attestation → Select one to implement the call chain.

Practice and Delivery

Press Experiment 6 Fixed version combination, output a reproducible record. Finally use the following CoVE Reading Map Conduct a design review; do not default to research implementation as a production plan.

Acceptance: TSM's code is very small, is TVM's TCB very small?

Not necessarily. It also needs to include the actual platform hardware, firmware, attestation roots, devices and guest internal components that it depends on. TCB depends on the protected object and deployment model, and is not equal to the code amount of a repository.

Elective order

Complete AIA / IOMMU and RVWMO first; then Zicfiss / Zicfilp control flow protection, cryptography extension, microarchitecture side channel according to position. V extensions and RTL are not on the shortest mainline to CoVE.

04 / LEARN BY OBSERVING

From disassembly to security review

Experiments 1–3 give the starting command, and 4–6 are source code and security analysis tasks. The command environment is written based on Ubuntu 24.04/Debian Linux; macOS recommends executing it in a Linux VM. The following is a learning recipe. This manual has not been run step by step in the target Linux environment, and the expected output will not be used as test results.

L1 · USER SPACE

Inspect the ABI and machine code of a C function

Install the cross tool chain and simulator, and compile Linux user mode programs. This selection rv64gc/lp64d matches common distribution tool chains; you are not required to learn floating point first.

sudo apt update
sudo apt install build-essential git gcc-riscv64-linux-gnu \
  binutils-riscv64-linux-gnu libc6-dev-riscv64-cross \
  qemu-user qemu-system-misc gdb-multiarch

mkdir -p riscv-lab1
cd riscv-lab1
cat > abi.c <<'C'
#include <stdint.h>
#include <stdio.h>
__attribute__((noinline))
int32_t add32(int32_t a, int32_t b) { return a + b; }
int main(void) { printf("%d\n", add32(40, 2)); return 0; }
C
riscv64-linux-gnu-gcc -O0 -g -march=rv64gc -mabi=lp64d -S abi.c -o abi-O0.s
riscv64-linux-gnu-gcc -O2 -g -march=rv64gc -mabi=lp64d -static abi.c -o abi
riscv64-linux-gnu-objdump -d -M no-aliases abi > abi.dis
riscv64-linux-gnu-readelf -h -A abi
qemu-riscv64 ./abi

Expected:Output 42; looks for 32-bit add and return sequence near add32. Comparing the stack frame of O0 to the leaf function of O2 does not require every compiler to generate the same text.

Troubleshooting:When the static link cannot find libc, check the cross libc development package; when the dynamic program cannot find the loader, use the matching sysroot to cooperate with QEMU -L. Don't treat user-mode QEMU as a full-machine emulator.

Acceptance product:Annotate a0/a1, a0 return value, ra, instruction length and ELF ABI; change add32 to an unsigned type to explain the semantics without relying on output appearance.

L2 · TRAP & PAGE TABLE

Stop a system call in xv6

First install a new enough QEMU according to MIT's current tool requirements; if the version of the distribution is too old, you should upgrade it before continuing. Keep the specific commits of the clone to avoid mixing the course experimental branch with the main repository.

git clone https://github.com/mit-pdos/xv6-riscv.git
cd xv6-riscv
git rev-parse HEAD
qemu-system-riscv64 --version
make TOOLPREFIX=riscv64-linux-gnu- qemu-gdb

Enter the same directory in the second terminal.make qemu-gdb The GDB port will be printed; replace PORT below with the actual port (not the fixed 1234).

gdb-multiarch kernel/kernel
(gdb) target remote localhost:PORT
(gdb) break usertrap
(gdb) continue
(gdb) p/x $scause
(gdb) p/x $sepc
(gdb) p/x $stval
(gdb) x/8i $pc

Observation:You may also encounter other traps when disconnecting for the first time, and scause should prevail. The exception code of user mode ecall is 8; it is different from the syscall number selected by the software.

Deliver:Read kernel/trampoline.S and kernel/trap.c, marking where registers are saved, paging tables, and sepc and sret are updated. Then complete MIT's page-table/trap lab and explain "which level of rejection" for a fault.

Troubleshooting:When the C breakpoint in the inline or assembly phase is not hit, use symbolic address breakpoints and disassembly;Ctrl-a x Exit QEMU. The startup and timer implementation of xv6 will change, read it according to your fixed commit.

L3 · FIRMWARE

Boot OpenSBI and observe the M → S handoff

This minimal experiment uses OpenSBI's own test payload and deliberately separates firmware observation and complete Linux image construction.

git clone https://github.com/riscv-software-src/opensbi.git
cd opensbi
git rev-parse HEAD
make CROSS_COMPILE=riscv64-linux-gnu- PLATFORM=generic
qemu-system-riscv64 -M virt -m 256M -smp 1 -nographic \
  -bios build/platform/generic/firmware/fw_payload.bin

Observation:OpenSBI banner, platform information, next-stage address and mode; the specific behavior of the built-in payload is subject to the version. If compilation fails, first check the minimum tool chain requirements of OpenSBI README.

Then do:Read QEMU virt startup instructions, boot Linux with parameters that match your kernel/rootfs; check a0/a1, satp and firmware reserved memory constraints. Log whether "firmware loading kernel" and "verifying kernel signature" actually occur.

L4 · TRANSLATION

Trace a guest address

Construct a paper example: GVA 0x4000 Mapped to GPA via VS-stage 0x8000, and then mapped to SPA 0x90008000. Revoke the permissions of the two stages respectively and deduce where to fall.

In your fixed Linux checkout, find the guest-page-fault and SBI dispatch paths from arch/riscv/kvm/ ; write down whether the host can modify the mapping and access the backing page.

Acceptance:Submit two conversion diagrams and a call chain; explain the new security requirements of ordinary KVM and confidential VM.

L5 · THREAT MODEL

Design a key release policy that can reject requests

Assuming that the host has been compromised, TVM needs to apply for a decryption key from the remote service. Draw the challenge, evidence, authentication strategy, session binding, and key delivery.

Inject counterexamples item by item: replay old attestation evidence, replace receiving public key, change startup page, double-fetch shared buffer, host never schedule.

Acceptance:The first three categories must be rejected; shared input needs to be verified; the last item should be identified as a usability problem and cannot be pretended to be automatically eliminated by TEE.

L6 · CoVE RESEARCH

Pin compatible versions and reproduce a TVM lifecycle

Select the dependency combination it explicitly supports from COVE PoC's README There is no unverified "one-click installation of the latest version of CoVE" here: the ABI, host kernel, TSM and QEMU branches must match.

  1. Record the specification commit, as well as the repository URL and commit of QEMU, OpenSBI/TSM, host kernel, guest image, and VMM; then record all build parameters.
  2. First run the workload that comes with the document and collect the logs of create → populate / measure → finalize → run → destroy. It is a summary of the life cycle for teaching purposes, and the actual function names are subject to the fixed draft.
  3. Confirm which isolation is provided by the simulation model and which capabilities are just stub/test keys; separate unimplemented capabilities such as attestation, device pass-through, migration, etc.
  4. Design negative use cases: reuse of owned pages, illegal life cycle calls, host access to private pages, incorrect attestation policy. Write "pass" only for actual observed results.

Graduation delivery:Version list, TCB diagram, page state transition diagram, at least three negative test records, and "this PoC cannot prove anything yet". If the environment cannot be reproduced temporarily, the source code review can be completed first and clearly marked as static analysis.

05 / THE DESTINATION

CoVE: from VM isolation to an untrusted host

Draft specification

The core scenario that COVE (Confidential VM Extension) focuses on is: the host OS/VMM participates in creating and scheduling TVM, but should not obtain the confidential memory and sensitive running status of TVM as a result. Specific assurances rely on platform implementation, hardware isolation, root of trust, and declared threat models. The picture below is a responsibility diagram for learning and does not represent the only execution mode or complete trust chain.

01 / OWNERWorkload owner

Defines images, allowed metrics, and key release policies.

02 / HOSTHost OS / VMM

Request resources, create and schedule TVM; can be regarded as a potential attacker according to the threat model.

03 / TRUSTEDTSM + TSM-driver

Perform protected operations, maintain TVM status and authorization; required hardware/firmware belongs to TCB.

04 / GUESTTVM

Run guest firmware, OS and workloads; collaborate with the host through controlled shares.

05 / VERIFIERProof verifier

Check the evidence, freshness, metrics and strategies to decide whether to deliver the secret.

Five boundaries to investigate

  1. Ownership:After a page is assigned from the host to the TVM, who can establish read-write or alias mappings?
  2. Conversion:When a private page is transferred to sharing/recycling, who is responsible for unmapping, synchronization, clearing and race prevention?
  3. Status:Where are vCPU registers, exception information, timers and interrupt status stored?
  4. I/O:Who controls access authorization for DMA and MMIO paths? Is the device itself trustworthy?
  5. Proof:What platform/TSM/TVM elements does the evidence cover? How does a validator bind a session?

Do not assume guarantees that are not specified

Availability:The draft threat model explicitly excludes denial of service caused by the host from the guarantee; the host can refuse to schedule.See original text

Physical and side channels:The attacker scope and mitigation measures are related to the platform solution, and unified coverage cannot be derived from the name "CoVE".View threat table

Device security:CPU memory access isolation does not automatically cover DMA; device pass-through read separately CoVE-IO draft.

Version status / 2026.09.23 check

RISC-V official H extension v1.0 In the approved specification library.AP-TEE / CoVE ABI repository Still clearly marked development, not ratified;Supervisor Domains / Smmtt repository It is an independent hardware isolation specification work. The existence of experimental code does not mean that all CoVE security attributes have been implemented; record the repository commit and review when reading Standard development dashboard.

Seven questions for reviewing a CoVE implementation

  1. What exactly are the capabilities to protect assets and host attackers?
  2. How to establish hardware isolation and TSM trusted startup?
  3. Is it possible for TVM private pages to be remapped, aliased or DMA accessed by the host?
  4. Who will complete the synchronization, clearing and error rollback of private ↔ shared conversion?
  1. Do exceptions, debugs, interrupts, and vCPU status leak sensitive data?
  2. Which TCB version does the attestation evidence cover? How to prevent replay and bind the session?
  3. PoC Which paths are real protection and which are simulations, stubs or future work?
